# وثيقة متطلبات النظام (SRS)
# Software Requirements Specification — واصل (Wasel)

**الإصدار:** 1.0  
**التاريخ:** 2026-08-17  
**المشروع:** واصل — نظام إدارة المفقودات  
**النطاق الجغرافي:** مدينة عتق، محافظة شبوة، اليمن

---

## 1. مقدمة

### 1.1 الغرض
تحدد هذه الوثيقة المتطلبات الوظيفية وغير الوظيفية لنظام واصل، وهو منصة رقمية تهدف إلى ربط أصحاب المفقودات بمن عثر عليها بطريقة آمنة وموثوقة.

### 1.2 النطاق
- **المستخدمون المستهدفون:** سكان مدينة عتق ومحافظة شبوة.
- **القنوات:** تطبيق ويب (Web App) يعمل على المتصفح (سطح مكتب + هاتف).
- **اللغة الأساسية:** العربية.

### 1.3 التعريفات والمصطلحات

| المصطلح | التعريف |
|---------|---------|
| **صاحب المفقود (Owner)** | المستخدم الذي أبلغ عن فقدان غرضه |
| **الملتقِط (Finder)** | المستخدم الذي عثر على غرض ونشر بلاغ عنه |
| **بلاغ المفقود (Lost Report)** | سجل `lost_items` في قاعدة البيانات |
| **بلاغ الموجود (Found Report)** | سجل `found_items` في قاعدة البيانات |
| **محرك المطابقة** | خوارزمية تحسب نقاط التشابه بين البلاغين |
| **التحقق العمياء (Blind Verification)** | آلية إثبات الملكية دون الكشف عن `secret_details` |
| **نقطة الأمانة (Pickup Point)** | موقع معتمد لتسليم المفقودات |
| **OTP** | رمز تحقق مرحلي يُرسل عبر الرسائل النصية |

## 2. المتطلبات الوظيفية

### 2.1 إدارة المستخدمين والمصادقة

| الرمز | المتطلب | الأولوية |
|-------|---------|---------|
| AUTH-01 | يجب أن يتمكن المستخدم من تسجيل الدخول برقم هاتفه عبر OTP | Must Have |
| AUTH-02 | يجب تخزين رمز OTP مُشفَّراً (hash) في جدول `otp_codes` مع وقت انتهاء الصلاحية | Must Have |
| AUTH-03 | يجب إنشاء جلسة في `sessions` بعد التحقق الناجح وتخزين رمزها في cookie آمنة (httpOnly) | Must Have |
| AUTH-04 | يجب أن يميز النظام بين دور `user` ودور `admin` | Must Have |
| AUTH-05 | يجب حذف الجلسة عند تسجيل الخروج | Must Have |

### 2.2 بلاغات المفقودات

| الرمز | المتطلب | الأولوية |
|-------|---------|---------|
| LOST-01 | يجب أن يتمكن المستخدم من إنشاء بلاغ مفقود يتضمن: العنوان، الوصف، التصنيف، تاريخ الفقدان، الإحداثيات، وتفاصيل سرية | Must Have |
| LOST-02 | يجب أن تبدأ حالة البلاغ بـ `open` تلقائياً | Must Have |
| LOST-03 | يجب ألّا تظهر `secret_details` في أي قائمة عامة أو استجابة بحث | Must Have |
| LOST-04 | يجب أن يتمكن المستخدم من تعديل بلاغه أو إغلاقه يدوياً | Must Have |

### 2.3 بلاغات الموجودات

| الرمز | المتطلب | الأولوية |
|-------|---------|---------|
| FOUND-01 | يجب أن يتمكن الملتقِط من إنشاء بلاغ موجود يتضمن: العنوان، الوصف، التصنيف، تاريخ الإيجاد، الإحداثيات، وتفاصيل سرية | Must Have |
| FOUND-02 | نفس قيود الحالة والخصوصية المطبَّقة على بلاغات المفقودات | Must Have |

### 2.4 محرك المطابقة الذكي

| الرمز | المتطلب | الأولوية |
|-------|---------|---------|
| MATCH-01 | يجب حساب نقاط التطابق بين كل بلاغ مفقود مفتوح وكل بلاغ موجود مفتوح | Must Have |
| MATCH-02 | يجب أن تشمل المتغيرات: تطابق التصنيف (weight: 0.40) + تداخل الكلمات النصية (weight: 0.35) + القرب الجغرافي بـ Haversine (weight: 0.25) | Must Have |
| MATCH-03 | يجب تخزين النتائج في جدول `matches` بحالة `suggested` | Must Have |
| MATCH-04 | يجب ألّا يُشغَّل المحرك إلا بشكل دوري (npm script أو server action) — لا queue | Must Have |
| MATCH-05 | يجب أن يتمكن صاحب البلاغ من قبول أو رفض أي مطابقة مقترحة | Must Have |

### 2.5 التحقق من الملكية (Blind Verification)

| الرمز | المتطلب | الأولوية |
|-------|---------|---------|
| VERIFY-01 | عند إنشاء المطالبة (claim)، يُرسَل سؤال التحقق من `secret_details` للمدعي دون الكشف عن الإجابة | Must Have |
| VERIFY-02 | يجب على المدير أو النظام مقارنة الإجابة مع `secret_details` والبت في المطالبة | Must Have |
| VERIFY-03 | تنتقل حالة المطالبة عبر: `pending → verified | rejected | cancelled` | Must Have |

### 2.6 نقاط الأمانة والاسترداد

| الرمز | المتطلب | الأولوية |
|-------|---------|---------|
| PICKUP-01 | يجب أن يتضمن النظام قائمة بنقاط الأمانة المعتمدة مع إحداثياتها | Must Have |
| RECOVERY-01 | بعد تأكيد المطالبة، يُنشأ سجل `recoveries` مرتبط بنقطة أمانة | Must Have |
| RECOVERY-02 | يجب تأكيد الاستلام من كلا الطرفين: `owner_confirmed_at` و `finder_confirmed_at` | Must Have |

### 2.7 البحث العام

| الرمز | المتطلب | الأولوية |
|-------|---------|---------|
| SEARCH-01 | يجب أن تكون قائمة البلاغات المفتوحة متاحة للعموم دون تسجيل دخول | Must Have |
| SEARCH-02 | يجب دعم الفلترة بالتصنيف، الحالة، والنص (العنوان والوصف) | Must Have |
| SEARCH-03 | يجب إخفاء `secret_details` في جميع نتائج البحث العام | Must Have |

### 2.8 الإشعارات

| الرمز | المتطلح | الأولوية |
|-------|---------|---------|
| NOTIFY-01 | يجب إنشاء إشعار داخلي (صف في `notifications`) عند اقتراح مطابقة جديدة | Should Have |
| NOTIFY-02 | يجب إنشاء إشعار عند تغيير حالة المطالبة | Should Have |
| NOTIFY-03 | يجب إنشاء إشعار عند تأكيد الاسترداد | Should Have |

## 3. المتطلبات غير الوظيفية

### 3.1 الأمان
- **SEC-01:** تخزين كلمات المرور ورموز OTP كـ hash (bcrypt أو sha-256 مع salt).
- **SEC-02:** الجلسات في PostgreSQL فقط — لا JWT مخزَّن في localStorage.
- **SEC-03:** حقل `secret_details` مُشفَّر على مستوى التطبيق قبل الحفظ (مرحلة لاحقة).
- **SEC-04:** جميع مسارات Dashboard محمية بـ `requireUser` middleware.
- **SEC-05:** جميع مسارات Admin محمية بـ `requireAdmin` middleware.

### 3.2 الأداء
- **PERF-01:** زمن استجابة صفحات البحث العام لا يتجاوز 800ms عند 100 بلاغ مفتوح.
- **PERF-02:** تشغيل محرك المطابقة لا يُعطّل الطلبات الجارية (تشغيل في الخلفية).

### 3.3 سهولة الاستخدام
- **UX-01:** الواجهة باللغة العربية بالكامل مع دعم RTL.
- **UX-02:** التصميم متجاوب يعمل على شاشات الهاتف (min-width: 320px).
- **UX-03:** رسائل الخطأ واضحة وبالعربية.

### 3.4 الموثوقية
- **REL-01:** جميع العمليات الحساسة تُسجَّل في `audit_logs`.
- **REL-02:** معاملات قاعدة البيانات (transactions) لانتقالات الحالة الحرجة.

---

## 4. قيود النظام

- لا يوجد تكامل مع خدمات رسائل SMS في المرحلة الأولى — OTP يُرسَل عبر واجهة المطور.
- لا يوجد دعع إشعارات Push — إشعارات داخلية فقط.
- التخزين المحلي للوسائط فقط (`uploads/`) — لا CDN في المرحلة الأولى.
